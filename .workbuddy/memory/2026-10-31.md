### DEV-003 关键结论（可复用）

1. **R 键失效的真实根因是中文输入法**：`e.key === 'r'` 在 IME 激活时拿到的是 `'Process'`（`isComposing=true`）。凡面向中文用户的网页键盘交互，一律改 `e.code` 物理键位。
2. **踩踏判定**：`player.vy > 1.2 && playerBottomPrev <= e.y + e.h * 0.6`，需用上一帧脚底位置，否则会漏判。
3. **必须加受伤硬直 `hurtStun`**：否则「侧碰被弹飞 → 落回同一只怪头上 → 踩死 → 奖励抵消惩罚」，惩罚形同虚设。这是逐帧追踪才发现的逻辑漏洞，不是代码报错。
4. **测试方法本身也会错**：DEV-001 曾因金币与角色同为橙色而误判「跳跃失败 0px」。定位像素时必须用角色专属配色。

### 建立的可复用测试手段

- Chrome DevTools Protocol：`--headless=new --remote-debugging-port` + WebSocket 驱动 `Runtime.evaluate` / `Input.dispatchKeyEvent` / `Page.captureScreenshot`
- **状态探针注入法**：读源文件 → 字符串替换注入 `window.__p` getter → 写临时 `.probe*.html` → 测试 → 删除。保证磁盘成品文件不被测试代码污染

## DEV-004 补充：R 键问题的真实根因（重要教训）

**DEV-003 的修复是无效的，而且我的测试给了我假的通过结论。**

当时只测了两种按键形态，漏了第三种：

| 形态 | e.code | e.key | keyCode | 结果 |
| --- | --- | --- | --- | --- |
| A 正常 | `KeyR` | `r` | 82 | ✓ |
| B 输入法 | `KeyR` | `Process` | 229 | ✓ |
| **C 输入法彻底接管** | **`''` 空** | `Process` | 229 | **✗** |

C 才是用户实际遇到的情况。`e.code === 'KeyR'` 在 code 为空时照样失效。

**根因不在代码，在测试方法**：我用 CDP 伪造了 `code:'KeyR'` 的事件，等于自己出题自己答。

### 最终方案（三重防线，不依赖"识别出 R"）

1. 按键判定三重兜底：`e.code` / `e.keyCode` / `e.key` 任一命中即算 R
2. 通关界面放宽为「按任意非操作键继续」——绕开"必须识别出 R"这个不可能的前提
3. 鼠标点击画布兜底，完全不经过键盘
4. `canvas` 加 `tabindex` 并主动抢焦点（解决预览面板 iframe 焦点问题）

### 必须记住的两个坑

- **`winLock` 递减要放在 `updatePhysics` 的 `state === 'win'` 提前返回之前**，否则通关后它永远是正数，锁死解不开。
- **「任意键继续」必须排除游戏操作键**。否则玩家按住方向键/空格冲线时，成绩画面一闪就被重开，根本看不到。已通过 `GAME_KEYS` / `GAME_VK` 两个白名单 + `e.repeat` + 45 帧锁定期解决。
